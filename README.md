# pi-text2video

Text-to-image for [pi](https://github.com/earendil-works): a `generate_image` tool the model can call, and an `/image` command for drawing on purpose.

Two backends:

- **`openai`** (default) — any OpenAI-compatible images API (`POST {baseUrl}/images/generations`): OpenAI itself, SiliconFlow, an internal gateway, one-api or a self-hosted service. Needs an API key; vendor-specific parameters pass through via `extraBody`.
- **`codex`** — uses an **existing Codex login**, no API key at all: the image is generated by Codex's server-side built-in image tool and billed to the ChatGPT plan the Codex CLI is signed in with. Two modes: `api` (default, calls the Codex backend directly, ~40s) and `cli` (drives `codex exec`, ~70s).

> The text2video in the repository name is where this is going; today it only does text-to-image.

## Install

```bash
pi install git:github.com/benenen/pi-text2video     # into user settings
pi install -l git:github.com/benenen/pi-text2video  # into this project only
pi install /path/to/pi-text2video                   # local directory
pi -e /path/to/pi-text2video                        # try it for one run
```

## Provider `codex`: use an existing Codex login

Codex's bundled `imagegen` skill prefers a built-in image tool that runs server-side inside a Codex turn — its SKILL.md states it "does not require `OPENAI_API_KEY`". This provider reuses that, so a plain `codex login` (ChatGPT account) is all the authentication there is.

Set it up from the login itself:

```
/image config import codex
```

That reads `$CODEX_HOME/auth.json`, picks the provider and mode that suit how codex is logged in, probes which model the account may actually use, and writes the result to `~/.pi/agent/text2image.json` (`--project` writes the project config, `--no-probe` skips the probing). The probe is a trivial text request per candidate — it never generates an image, and an unsupported model is rejected before any work happens.

Or write it by hand:

```jsonc
// ~/.pi/agent/text2image.json — no key anywhere
{ "provider": "codex" }
```

or per run: `PI_TEXT2IMAGE_PROVIDER=codex pi`.

### `codexMode: "api"` (default)

Reads the tokens `codex login` stored in `$CODEX_HOME/auth.json` and calls the Codex backend directly: one Responses request carrying an `image_generation` tool, and the PNG comes back as base64 in an `image_generation_call` item. About 40s per image.

- Tokens are read at call time and sent to the Codex backend only. They are never written anywhere, never logged, and a refreshed access token stays in memory for the pi session instead of being written back to `auth.json`.
- Expired access tokens refresh automatically (`codexRefresh: false` turns that off); a 401 triggers one refresh and one retry.
- `codexApiModel` must be a model the account may use with Codex. On a ChatGPT plan `gpt-6-astra` works and the `gpt-5.x` names are rejected with *"model is not supported when using Codex with a ChatGPT account"* — the error says so and names the fix.
- This is a private protocol with no compatibility promise, and the request identifies itself with the same `originator` the Codex CLI sends. If it ever breaks, switch to `"codexMode": "cli"`.

### `codexMode: "cli"`

Runs `codex exec` and collects whatever Codex wrote under `$CODEX_HOME/generated_images` (matched by modification time). Slower — about 70s, since it is a whole agent turn — but it touches no tokens and keeps working across protocol changes. Requires `codex` on `PATH` and a working login (`codex login status`).

### Both modes

- Codex picks the resolution and the image model; `size` is a hint and the `model` parameter is ignored. For exact control use the `openai` provider.
- Each image is billed to the ChatGPT plan, not to an API account.

### Proxy

Node's `fetch` ignores `HTTPS_PROXY`, and the Codex proxy normally lives in `$CODEX_HOME/.env` where pi never sees it — so this extension reads that file itself and tunnels through the proxy with CONNECT (Basic credentials included). Precedence: explicit config → `$CODEX_HOME/.env` → the process environment, with `NO_PROXY` honoured. It applies to the `openai` provider too.

## Configuration

Merged highest first: environment variables → project config `./.pi/text2image.json` → user config `~/.pi/agent/text2image.json` → defaults.

| Field | Environment variable | Default | Notes |
| --- | --- | --- | --- |
| `provider` | `PI_TEXT2IMAGE_PROVIDER` | `openai` | `openai` or `codex`; the fields below marked *(openai)* only apply to the former |
| `baseUrl` *(openai)* | `PI_TEXT2IMAGE_BASE_URL` | `https://api.openai.com/v1` | `/images/generations` is appended; a full endpoint is also accepted |
| `apiKey` *(openai)* | `PI_TEXT2IMAGE_API_KEY` | empty | when empty no `Authorization` header is sent (common for internal gateways) |
| `model` *(openai)* | `PI_TEXT2IMAGE_MODEL` | `gpt-image-1` | |
| `size` | `PI_TEXT2IMAGE_SIZE` | `1024x1024` | set to `""` to omit the field entirely |
| `outputDir` | `PI_TEXT2IMAGE_OUTPUT_DIR` | `.pi/images` | relative to the working directory, `~` supported |
| `timeoutMs` | `PI_TEXT2IMAGE_TIMEOUT_MS` | `180000`; `300000` codex/api; `600000` codex/cli | 30-90s per image is normal, do not set this too low |
| `responseFormat` | `PI_TEXT2IMAGE_RESPONSE_FORMAT` | not sent | set `b64_json`/`url` only if the service demands it; gpt-image-1 returns 400 when it sees the field |
| `headers` | `PI_TEXT2IMAGE_HEADERS` (JSON) | `{}` | extra request headers |
| `extraBody` | `PI_TEXT2IMAGE_EXTRA_BODY` (JSON) | `{}` | merged into the request body, for `negative_prompt`, `guidance_scale` and friends |
| `useCodexAuth` *(openai)* | `PI_TEXT2IMAGE_USE_CODEX_AUTH` | `true` | fall back to an existing codex API-key login for the key, see below |
| `codexMode` *(codex)* | `PI_TEXT2IMAGE_CODEX_MODE` | `api` | `api` or `cli` |
| `codexApiModel` *(codex/api)* | `PI_TEXT2IMAGE_CODEX_API_MODEL` | `gpt-6-astra` | must be a model the account may use with Codex |
| `codexBaseUrl` *(codex/api)* | `PI_TEXT2IMAGE_CODEX_BASE_URL` | `https://chatgpt.com/backend-api/codex` | |
| `codexRefresh` *(codex/api)* | `PI_TEXT2IMAGE_CODEX_REFRESH` | `true` | refresh expired access tokens in memory |
| `codexOriginator`, `codexTokenUrl` *(codex/api)* | `PI_TEXT2IMAGE_CODEX_ORIGINATOR`, `…_TOKEN_URL` | Codex CLI values | escape hatches if the protocol moves |
| `codexClientId` *(codex/api)* | `PI_TEXT2IMAGE_CODEX_CLIENT_ID` | the `aud` of the stored `id_token` | OAuth client for token refresh; derived at runtime, override only if that fails |
| `codexCommand` *(codex/cli)* | `PI_TEXT2IMAGE_CODEX_COMMAND` | `codex` | the Codex CLI to run |
| `codexModel` *(codex/cli)* | `PI_TEXT2IMAGE_CODEX_MODEL` | Codex default | agent model for the turn, not the image model |
| `httpProxy`, `httpsProxy`, `noProxy` | — | from `$CODEX_HOME/.env`, then the environment | see Proxy above |

`baseUrl` and `apiKey` fall back to `OPENAI_BASE_URL` / `OPENAI_API_KEY` when unset.

Examples:

```jsonc
// OpenAI
{ "baseUrl": "https://api.openai.com/v1", "apiKey": "sk-...", "model": "gpt-image-1", "size": "1024x1024" }

// SiliconFlow
{ "baseUrl": "https://api.siliconflow.cn/v1", "apiKey": "sk-...", "model": "Qwen/Qwen-Image",
  "extraBody": { "negative_prompt": "lowres, watermark" } }

// Internal OpenAI-compatible gateway, no key
{ "baseUrl": "http://172.31.0.1:16777/v1", "apiKey": "", "model": "flux-dev", "timeoutMs": 300000 }
```

### Borrowing a codex API key (provider `openai`)

A Codex login can also just supply the key. When no key is configured for this extension and `OPENAI_API_KEY` is unset, `~/.codex/auth.json` (or `$CODEX_HOME/auth.json`) is consulted:

- **API-key login** — `printenv OPENAI_API_KEY | codex login --with-api-key` stores the key as `OPENAI_API_KEY` in `auth.json`; it is an ordinary key and is used as-is. `/image config` shows which file it came from.
- **ChatGPT account login** (`auth_mode: "chatgpt"`) — no key to borrow. Those tokens are scoped to the Codex backend, and `api.openai.com` rejects them with `403 … missing scopes`. `/image config` and every 401/403 say so and point at `provider: "codex"`, which is the way to use that login.

Precedence: this extension's config or env → `OPENAI_API_KEY` → codex. Set `"apiKey": "codex"` to require the codex credential (and get a clear error when it is absent), or `"useCodexAuth": false` / `PI_TEXT2IMAGE_USE_CODEX_AUTH=0` to ignore it entirely. Nothing is ever copied out of `auth.json`: it is read at call time.

`/image config` prints the configuration as it was actually resolved (key redacted) — the fastest way to find out which file was picked up.

## Usage

**From the model**: just ask for a picture and it calls `generate_image`. Parameters: `prompt`, `n` (1-4), `size`, `model`, `filename`.

**By hand**:

```
/image a red panda drinking tea, watercolour
/image a neon city skyline --n 2 --size 1536x1024
/image --model flux-dev "a logo for a coffee shop"
/image                     # no arguments opens an input dialog
/image config              # show the current configuration
/image config import codex # configure from an existing Codex login
```

The two paths differ in exactly one way: `/image` results stay in the TUI and never enter the LLM context, while `generate_image` results do, so the model can comment on them and iterate on the prompt.

## About the images

- **Every result records where it came from**: provider, the interface actually called, and the model. It shows in the tool output, in the `/image` card, and in the session entry, so an image found weeks later can be traced back:

  ```
  ✓ 1 image(s) · codex/api · gpt-6-astra · 56.1s
    POST https://chatgpt.com/backend-api/codex/responses (tool: image_generation)
    /path/to/.pi/images/20260916-173420-a-brass-compass….png (1370×1148, 2.3 MB)
  ```
- **Reported dimensions are the file's own**, read from its header. The configured `size` is a request: the codex backend picks its own resolution and OpenAI-compatible services round or ignore it, so results are labelled `requested size` and each file reports what it actually is.
- Images are **always written to disk** first, by default under `.pi/images/`, named `timestamp-prompt-slug.png`; collisions get a numeric suffix.
- Inline previews need a terminal that speaks an image protocol (kitty, iTerm2, Ghostty, WezTerm, Warp); the kitty protocol only accepts PNG. Elsewhere you get the paths, and nothing else is lost.
- Only models with image input get images inlined into the context, at most 2 images and 4MB each; otherwise the model just gets the paths, so no tokens are wasted.

## Development

```bash
npm test                          # everything below
node test/client.test.mjs         # config resolution + images client
node test/proxy.test.mjs          # proxy resolution + a real CONNECT tunnel
node test/codex-auth.test.mjs     # borrowing an API key from an existing codex login
node test/codex-api.test.mjs      # codexMode api, against a fake Codex backend
node test/codex-import.test.mjs   # /image config import codex
node test/codex-backend.test.mjs  # codexMode cli, against a fake codex binary
node test/extension.test.mjs      # tool, command and renderers against a fake pi API
```

The tests install nothing: they borrow pi's own jiti to load the `.ts` files and create a symlink at the repository root pointing at pi's `node_modules` (gitignored), which also lets editors resolve `typebox` and `@earendil-works/*`. If pi lives somewhere unusual, point `PI_PACKAGE_DIR` at it.

```
extensions/text2image.ts   tool + /image command + TUI rendering
src/config.ts              configuration and credential resolution (env → project → user → codex → defaults)
src/images.ts              provider dispatch, OpenAI-compatible images client, saving to disk
src/codex-api.ts           codexMode api: Codex backend, tokens from auth.json, SSE
src/codex-import.ts        /image config import codex: detect, probe, write config
src/codex-backend.ts       codexMode cli: runs `codex exec`, collects what it generated
src/http.ts                dependency-free HTTP with CONNECT proxy tunnelling
src/proxy-env.ts           proxy resolution ($CODEX_HOME/.env → environment)
```
